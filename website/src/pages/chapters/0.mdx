# 0. The examples pass. Did the agent gain permission?

The model's output is untrusted: it can be wrong, it can be steered by content it reads, and it changes between versions. The policy and the boundary are what we trust, and this course is about making that trust precise, observable, and provable where proof applies.

**The task.** A research assistant reads `workspace/measurements.csv`, fetches reference data with `GET /reference` from `reference.fixture` through the proxy, and writes `workspace/results/report.md`.

<EvidenceBanner label={data.label} />

## Predict

<details>
<summary>Will the agent's GET succeed? Yes / no / depends on the policy.</summary>

It depends on the policy. Under P0 the request is <Label term="allowed" /> because the permit `get-reference` matches a GET to `/reference`. The tempting answer is "yes, it is the agent's task". A task says what the agent should try; it grants nothing.

</details>

## Intervene: broaden one predicate

P1 changes one thing: `get-reference` now accepts GET or POST. The endpoint, the path, and the connection policy stay the same.

<Run run={data.run_p1} title="The same agent, unchanged, under P1" />

The original example still passes.

## Verify

<details>
<summary>After broadening to GET-or-POST, did permission expand? No, the tests pass / yes / cannot tell from tests.</summary>

Yes. The tests only tried GET, so they could not tell. The solver searched every request in the domain and returned the one the tests never tried.

</details>
